# 飞书个人会话总结助手需求文档

版本：v0.1（首版试点）  
日期：2026-09-30  
状态：需求草案，可用于技术评估与开发拆分

修订说明：补充管理员后台，纳入首版交付，支持授权用户查询、任务执行历史与执行结果查看。

编码前补充：区分身份登录与消息授权，补充接口鉴权验收；技术实现以技术设计 v0.2 为准，文档文件名保留以兼容已有链接。

## 1. 背景与目标

公司日常通过飞书沟通，员工需要从私聊、群内提及和自己发出的消息中回顾工作信息。希望提供一个个人助理，每天按员工自行设置的时间，汇总过去 24 小时的相关消息，并将总结私发给本人。

首版目标：同一公司内至少 2 名真实员工能同时启用，各自完成授权、设置时间、接收仅属于自己的总结，持续运行，无需开发人员每天手工触发。

本版首先验证“每天集中回顾相关消息”是否有用。跨天承诺追踪、自动催办等属于后续方向，不作为首版交付要求。

## 2. 用户与使用方式

| 角色 | 需求与权限 |
|---|---|
| 普通员工 | 开启自己的助理，授权读取本人可访问的消息，设置时间，查看本人总结，暂停或停用 |
| 试点管理员 | 通过后台查看本公司已接入用户的授权与启用状态、任务执行历史及结果；产品界面不提供其他员工聊天正文或总结内容的查看功能 |

一个内部应用服务多名员工，每人拥有独立配置和数据访问边界。首版向至少 2 人开放，后续可扩大应用可用范围；本版不要求完成全公司规模验证。

## 3. 首版范围与边界

### 3.1 必须支持

- 飞书内入口及首次启用流程。
- 每位员工独立授权、独立设置每日执行时间。
- 收集指定 24 小时窗口内的三类消息：个人私聊、群内明确 @本人、本人发出的消息。
- 解析文本和富文本；对其他消息类型保留可识别的信息与未解析标记。
- 按话题整理摘要，展示重要内容、行动项及原消息来源。
- 每天自动执行，并通过飞书私聊发送给本人。
- 手动“立即总结”，用于首次体验和故障后的主动重试。
- 暂停、恢复、停用及授权失效处理。
- 多用户隔离、分页与去重、失败重试、覆盖范围与缺失情况提示。
- 管理员后台：授权用户列表、任务历史列表、任务结果详情，以及独立的管理员访问控制。

### 3.2 首版不包含

- 未 @本人、且本人未发言的普通群消息全量总结。
- 跨天维护任务完成状态、自动催办、自动回复同事。
- 自动创建或修改飞书任务、日历、工单。
- 图片 OCR、语音转写、视频理解、附件全文解析、链接指向文档的全文读取。
- 管理员查看员工消息、团队汇总报告、绩效评价。
- 多公司租户运营、商业计费、全公司容量承诺。

外部用户私聊、外部群和受保护会话不作为首版必达场景；实际遇到时，按接口可访问范围处理，并披露未覆盖范围。

## 4. 核心用户流程

1. 员工进入助理，看到用途、消息范围、数据处理说明及授权入口。
2. 员工完成个人授权，选择每日执行时间，确认开启。
3. 系统显示状态，例如：“已开启，每天 19:00 开始总结，完成后私发给你。”
4. 员工可点击“立即总结”验证效果；手动运行不改变每日计划。
5. 每天到期后，系统读取该员工对应时间窗口内的消息，生成并私发总结。
6. 员工可调整时间、暂停或停用；授权失效时可重新授权。

首版入口可使用机器人卡片配合简单设置页。具体交互载体由实现选择，但上述操作应由员工自助完成。

身份登录与消息授权分开：仅登录不代表允许读取消息。消息授权失效或停用后，用户仍可登录查看自己的状态；退出网页登录不自动停止已开启的每日任务。暂停只停止自动执行，暂停后仍可主动“立即总结”；暂停时已运行的任务按取消规则处理。

## 5. 消息范围与统计口径

### 5.1 三类消息

| 类别 | 纳入规则 |
|---|---|
| 私聊 | 本人与其他人的一对一会话中，统计窗口内双方发送的消息 |
| 群内 @本人 | 统计窗口内明确提及本人账号的群消息，按身份标识判断，不以文本中出现姓名作为依据 |
| 本人发出 | 统计窗口内本人在可访问的私聊及群聊中发出的消息 |

三类消息取并集，以消息 ID 去重。私聊中本人发出的消息仅处理一次。

首版默认不将仅 @所有人的群消息作为直接命中；消息同时明确 @本人时纳入。机器人通知、系统提示和助理自身生成的总结默认排除，避免重复总结自己的输出。

### 5.2 统计窗口

- 首版统一使用北京时间（Asia/Shanghai）。
- 每日设置时间为统计截止时间和任务计划启动时间，不保证该分钟内完成推送。
- 例如 9 月 30 日 19:00 的任务，统计区间为 `[9 月 29 日 19:00, 9 月 30 日 19:00)`。
- 根据消息发送时间判断是否落入窗口，不以消息是否已读为筛选条件。
- 任务延迟或重试时保持原计划窗口不变，不使用重试时刻重新计算窗口。
- 手动总结以点击时刻为截止时间，统计之前 24 小时，并标记“手动总结”。
- 员工修改时间后，以新的下一次计划时间计算窗口；可能与上一份总结重叠或出现间隔，界面应说明，不自动改成“自上次总结以来”。
- 首次开启及暂停后恢复，均从下一次未来的计划时间开始；不自动补发此前日期。

### 5.3 上下文与完整性

- 对含指代、回复关系或话题讨论的消息，可补充本人有权限访问的相关上下文，避免孤立解读。
- 上下文应围绕命中消息或所属话题展开，不因补充上下文而总结整个无关群聊。
- 窗口外的上下文可以用于解释，但不能被描述为本次窗口内的新进展。
- 分页必须读取到结束；不允许仅处理第一页后声称完成。
- 搜索结果不全、限流导致中断、正文读取失败、话题未展开等情况必须记录并影响覆盖状态。
- 不能仅凭“接口请求成功”判断全量完整，也不能把搜索展示片段当作完整正文。
- 已撤回或已删除的消息不用于生成实质结论；编辑过的消息以读取时可获取的最新正文为准。

### 5.4 非文本内容

文本和富文本为首版必达类型。卡片在可解析时提取可读文字；图片、语音、视频、文件、合并转发等未完整解析的消息保留类型、可用名称或来源，并标记“未解析内容”。不得根据文件名或占位符编造内容。

## 6. 功能需求

| 编号 | 功能 | 首版要求 |
|---|---|---|
| F01 | 身份识别与授权 | 将当前用户与其授权凭证正确绑定；用户不能输入其他人的 ID 来读取其消息 |
| F02 | 个人配置 | 保存启用状态、每日时间、时区、授权状态、下次执行时间 |
| F03 | 定时执行 | 不同用户按各自时间运行；同一时间启用时也能分别完成任务 |
| F04 | 消息采集 | 按三类规则采集、分页、去重、过滤，读取正文并按需补充上下文 |
| F05 | 总结生成 | 按话题整理内容、重要决定及行动项，保留来源，不编造责任人或截止时间 |
| F06 | 本人推送 | 仅向该总结所属用户发送；内容过长时分段，保持编号和阅读顺序 |
| F07 | 立即总结 | 可手动触发最近 24 小时的总结；同一用户重复点击时提示已有任务运行 |
| F08 | 暂停与恢复 | 暂停后不创建新的定时任务；恢复后显示新的下次执行时间 |
| F09 | 停用 | 停止后续采集和推送、删除本地授权凭证，并按保留规则清理消息数据 |
| F10 | 异常反馈 | 区分无消息、部分完成、采集失败、生成失败、发送失败和需要重新授权 |
| F11 | 管理员后台 | 管理员可查看本公司授权用户列表、任务历史及结果详情；支持筛选、分页，不展示正文 |

暂停或停用时，正在处理的任务应在下一个可取消阶段停止；发送前再次检查用户状态。已经成功发送到飞书的消息不自动撤回。

### 6.1 管理员后台页面

管理员通过 Web 的“管理后台”入口进入，首版包含以下三个页面。普通员工不能访问这些页面或对应接口。

**页面一：授权用户列表**

- 默认查看当前有效授权且未停用的用户，包括已开启和已暂停的用户；可切换查看全部已接入用户、需要重新授权或已停用用户。
- 展示：姓名、用户标识、首次授权时间、最近授权时间、授权状态、授权最近检查时间、助理启用状态、每日时间、下次执行时间、最近任务结果。
- 支持按姓名或用户标识搜索，按授权状态和启用状态筛选，分页展示。
- 点击某个用户，可跳转到仅显示该用户任务的历史列表。
- 区分授权和启用：已授权不等于已开启；暂停不等于撤销授权。
- 授权状态以最近一次授权、刷新或 API 检查结果为依据；展示最近检查时间，不承诺即时感知用户在飞书侧的撤销。

**页面二：任务执行历史**

- 默认查看最近 7 天的全体已接入用户任务，可在保留期限内查询。
- 展示：任务 ID、所属用户、定时/手动触发、计划时间、实际开始与结束时间、统计窗口、执行状态、覆盖状态、送达结果及耗时。
- 支持按用户、日期范围、触发方式、执行状态、覆盖状态和送达状态筛选，按时间倒序分页。
- 尚未执行、正在执行、部分完成、无消息、失败、取消、错过计划、发送结果待确认均需有明确展示。

**页面三：任务结果详情**

- 展示任务各阶段的开始时间、耗时、状态和重试次数。
- 展示采集数量、去重数量、未解析数量、正文读取失败数量及已知覆盖缺口。
- 展示发送分段总数、成功/失败/待确认分段、发送时间和可用的飞书消息 ID。
- 展示经脱敏的失败原因和建议处理方式，例如“用户需要重新授权”“被限流，自动重试已结束”。
- “执行结果”指执行是否完成、覆盖情况及是否送达，不包含员工消息原文、生成的总结正文、模型输入输出或授权令牌。

首版后台以查询为主，不提供代用户授权、修改个人配置、强制重跑或重新发送。管理员身份由部署配置指定；不因某人是飞书管理员就自动取得本应用后台权限。

## 7. 总结内容要求

### 7.1 输出结构

1. 标题及统计区间。
2. 今日概览：用少量文字概括主要话题。
3. 重要进展与决定：按项目或话题归类。
4. 与我有关的行动项：明确要求、待确认事项、本人承诺；没有则写“未发现明确行动项”。
5. 原消息来源：每条重要结论可追溯到对应消息。
6. 覆盖情况：去重后获取数量、未解析数量、读取失败或可能遗漏的范围。

信息较少时缩短输出，不为填满模板制造内容。没有命中消息且采集成功时，发送简短“本时段未发现符合范围的消息”，不生成空泛日报。

### 7.2 内容质量

- 区分“讨论中的提议”和“已经确认的决定”。
- 仅在原文明确时提取责任人、承诺和截止时间；不明确时标注“待确认”。
- 可以指出“在已获取记录中未见明确回复”，不得据此断言用户未处理。
- 不要求逐条复述全部消息；去除寒暄和重复信息，同时保留有实质信息的话题。
- 原消息跳转链接应在试点中验证；若无法生成可用链接，需提供会话、时间和消息标识作为替代定位信息，并说明限制。
- 聊天内容只作为总结素材，不能改变助理的收件人、权限或执行规则。

### 7.3 覆盖状态

| 状态 | 含义及展示 |
|---|---|
| 采集完成 | 已完成本次可访问范围的采集，未检测到已知缺失；不承诺平台不可访问内容也已覆盖 |
| 部分完成 | 存在明确失败、未解析内容或搜索不全提示；在总结顶部标出，并说明影响范围 |
| 未能生成 | 主要数据未取得或总结生成失败；发送简短失败说明，不输出误导性空总结 |

## 8. 调度、重试与可用性

- 同一用户同一计划时间只产生一个有效定时任务；重启或调度重复触发不应重复推送。
- 用户之间的任务相互隔离：A 的授权失败或大消息量不应阻塞 B 的任务。
- 对临时失败进行有上限的退避重试；首版建议最多自动重试 3 次，具体间隔由接口限流要求确定。
- 对权限失效不反复重试，应提示重新授权。
- 发送结果不确定时先核对发送状态或使用接口幂等机制，避免盲目重发；无法核对时标记待处理。
- 服务必须能在用户个人电脑关闭后继续按时工作。
- 短暂服务中断后，建议补执行距计划时间不超过 2 小时的任务，保持原窗口并标记延迟；超过该范围不自动批量补发，记录错过任务并提供手动总结入口。

首版性能目标：在双方各不超过 1,000 条去重命中消息、无附件全文解析、上游服务正常的试点条件下，任务在计划时间后 1 分钟内开始，95% 在 10 分钟内完成推送。该数值是拟定验收目标，需通过接口容量测试确认，不能当作已验证能力。

## 9. 数据与权限要求

- 读取依赖用户本人授权；应用可用范围不能替代个人数据授权。
- 配置、缓存、正文、摘要和任务记录均绑定公司及用户身份；共享群消息也不能导致跨用户摘要串用。
- 授权凭证加密保存，不写入日志、不暴露到前端。
- 默认运维日志只保留状态、数量和错误信息，不记录聊天正文和模型完整输入。
- 模型服务采用公司允许处理此类工作消息的服务；首次启用时说明数据用途和处理范围。
- 拟定保留规则：服务端原始正文和临时摘要在任务结束后 24 小时内清理；不含正文的任务记录保留 30 天。用户停用后立即删除凭证，并在 24 小时内清理其缓存正文和摘要。
- 已推送至飞书的总结随该会话保留，服务端清理不代表飞书消息也被删除；启用说明中应明确这一点。

## 10. 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A01 | 两人独立使用 | A、B 分别授权并设置不同时间，均按自身配置收到总结；修改 A 配置不影响 B |
| A02 | 同时运行 | A、B 设置相同时间，两份任务分别完成且无串数据、串收件人 |
| A03 | 三类消息覆盖 | 在可访问的内部测试会话中构造私聊收发、明确 @本人、本人群内发言，所有符合规则的测试消息均被采集 |
| A04 | 排除与去重 | 普通群聊、仅 @所有人、助理自身输出按规则排除；重复命中消息仅处理一次 |
| A05 | 分页与窗口 | 使用超过单页的数据量验证完整分页；窗口起止边界及延迟重试时的窗口正确 |
| A06 | 上下文 | “按第二个方案做”等测试消息能结合可获取上下文解释；不能获取时明确表示信息不足 |
| A07 | 来源与准确性 | 测试集中的决定、责任人和时间与原文一致；重要结论有可验证的定位信息 |
| A08 | 无消息与失败 | 成功采集但无命中、授权失败、部分读取失败分别展示，不能互相混淆 |
| A09 | 非文本内容 | 测试图片、文件等未解析消息明确标记，不生成虚构内容 |
| A10 | 暂停及停用 | 暂停后不再定时发送，恢复后按新计划运行；停用后停止采集并按规则清理 |
| A11 | 重试与重启 | 重复调度、临时错误和服务重启不造成同一计划重复推送；发送不确定状态有处理记录 |
| A12 | 持续运行 | 至少 2 人连续试用 7 天，个人电脑关闭不影响运行；记录全部计划任务的成功率、耗时及异常 |
| A13 | 数据隔离 | A 无法通过界面或请求访问 B 的配置、正文及总结；运维界面不暴露消息正文 |
| A14 | 管理员用户列表 | 管理员可区分 A、B 的有效授权、需重新授权、暂停和停用状态；搜索、筛选、分页及最近检查时间正确 |
| A15 | 管理员任务历史 | 可按用户、时间、触发方式和状态查询任务；点击用户能正确过滤其任务，列表与详情数据一致 |
| A16 | 管理员结果详情 | 能查看成功、无消息、部分完成、失败及送达待确认的阶段、计数与错误说明，不展示正文或凭证 |
| A17 | 管理员鉴权 | 普通用户即使直接访问后台 URL 或 API 也被拒绝；管理员仅能查看本公司数据；访问记录可审计 |
| A18 | API 鉴权与 CSRF | 未登录、过期或伪造会话不能获取业务数据；缺失/错误 CSRF 的修改请求被拒绝；A 不能读取 B 的任务 |
| A19 | 登录与授权分离 | 消息授权失效后仍可仅身份登录查看状态和停用；管理员只登录不自动授权消息；退出登录不停止已授权任务 |
| A20 | 恢复与一致性 | 多日停机不漏掉仍可补执行的计划；部分发送后重启不重复发送成功分段；恢复配置备份后不会自动补发历史报告 |

正式判定试点通过前，所有必达功能验收项应通过。覆盖测试针对可控测试消息逐条核对，不仅凭摘要读起来通顺判断成功。

## 11. 试点效果评估

连续 7 天记录两类指标：

- 运行质量：应执行次数、成功推送次数、部分完成次数、失败次数、耗时、重复推送次数。
- 使用价值：用户是否阅读、是否发现原本可能遗漏的信息、是否因此采取行动、是否愿意继续使用。

阅读与行动反馈由用户主动反馈或简单访谈取得，不假设能读取所有消息的真实阅读状态。“文字写得好”不单独作为继续投入的理由。

## 12. 交付阶段与技术前置验证

### 阶段一：消息可访问性验证

用至少 2 个真实账号验证三类消息的搜索、正文读取、分页和私发本人。重点验证机器人不在群内时的用户身份读取边界、私聊权限、话题回复、搜索结果不全提示及消息定位链接。

该阶段只判断接口是否满足需求。若某类必达消息无法获得，不得直接删除该需求并宣称首版完成，应记录缺口并调整方案或由产品明确变更范围。

### 阶段二：完成首版闭环

完成授权与配置、每日调度、消息处理、总结生成、本人推送及异常提示，让两名员工自助启用；同时交付管理员用户列表、任务历史及结果详情页面。

### 阶段三：连续试点

运行至少 7 天，完成验收和用户反馈，决定是否扩大到更多员工。

## 13. 本文拟定的默认项

以下是为推进首版而提出的默认值，并非此前已经确认的用户要求：

- 每天执行，含周末；北京时间；设置页默认建议 19:00，由用户确认启用。
- 排除仅 @所有人及机器人通知。
- 设置时间为开始处理时间，允许总结稍后送达。
- 先保证文本、富文本，其他内容披露未解析情况。
- 不提供服务端历史总结浏览页，历史结果在飞书会话中查看。
- 正文临时保留 24 小时、无正文任务记录保留 30 天。
- 性能目标、重试次数和中断补执行窗口按第 8 节作为首版拟定值。

这些默认项可在开发评审中修改；调整时应同步更新统计规则和验收用例。
